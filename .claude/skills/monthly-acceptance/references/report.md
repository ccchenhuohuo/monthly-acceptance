# 报告

交付物是一篇文字报告 `RUN/报告.md`，给用户读、由用户转发。骨架见 `assets/report-template.md`。

## 结构

1. **结论**：放行 / 有保留放行 / 打回，一句话理由；再 3–7 条要点，每条一句结论加一句支撑数字。能被下游直接引用的判断放最前。
2. **模块状态**：12 个模块逐一 ✅ / ⚠️ / ⏸️ 加一句话。正面确认与问题同等呈现；没查成的写原因与补查条件，不写成正常。
3. **重点问题**：按对我们所用数字的影响排序。每条按排查逻辑逐层写：现象 → 已做检查 → 排除了什么 → 定性 → 置信 → 影响 → 证据位置。下钻叙事写到具体 SPU / ASIN 与平台路径。
4. **需服务商核对的事项**：逐条写对象（站点、平台路径、product_id）、现象与量级、请服务商确认或说明的具体内容。这是唯一出现“请…”的地方。
5. **与历史的对照**：本期观察与变迁台账、已知缺陷台账、案例库的关系——一致 / 新增 / 已修复 / 不再出现；新现象记入变迁台账哪一栏。
6. **口径与边界**：数据月、源表更新时间、现役发布、运行期间是否有变；未查的、受限的、推断的分别注明。

## 写法

- 给业务同事讲清楚的语态，通俗、指代清楚；不出现状态码、文件内部字段名、规则编号。
- 两套口径每处标明：标准类目（我们的口径）还是平台类目（服务商的口径）。
- 金额写本币与币种，不跨站点相加；份额写明是件数还是金额口径，品牌排名两个口径并列。
- 三种状态分开说：无观测（没有数据）、零暴露（问题只在“其他”或未打标里）、未发现异常（查了没问题）。
- 已证缺陷、未解决风险、普通变化分开写；贡献是分解不是因果；敏感性分析不冒充修正后的真实值。
- 推断标“推断，待确认”；服务商说法注明来源与日期。
- 报告不写处置，不自动发送。
- 每个关键数字都能回到运行目录里落盘的 SQL 和结果：在证据位置写 `views/<视图>.csv` 或 `queries/<名>.csv`。
