# 判定方法

开工必读。这里是方法与长期有效的数据事实；具体事件的历史判断在项目台账里，形成本期观察之后才对照（见 SKILL.md 第 6 步）。

## 1. 数据事实（2026-10 起）

**一张源表** `internal.flywheel.monthly_sales_wide`，每行 = 站点×平台×商品×SKU×月。服务商每月全量重推，历史月每次都是新生成的。

| 事实 | 判读含义 |
|---|---|
| 平台类目 category_1..5、sub_category（Amazon 最多 9 级，完整链在 sub_category） | 定根因、写给服务商用平台路径 |
| AI 标准类目 std_category_1..3，取值来自 VIJIM 标准（7 个一级、108 个三级） | 我们的消费口径；打标由服务商做，打标错误是交付缺陷 |
| std_category_1 = “其他” 为非关注品类（含暴力风扇、清洁工具、烟雾机等），为空 = 未打标 | 关注口径 = 非空且非“其他”；未打标的行应接近零 |
| 8 个属性标签（色温、适配品牌、连接方式、安装方式、驱动方式、传输方式、材质、无线充） | SKU 级切片维度，不进份额分母；只在适用叶子上有意义 |
| 件数 count ≥ 1，没有 0 件行；金额 discount_sales = 到手价 × 件数；page_price ≥ discount_price（2026-09 逐行核对均成立，旧表时期也没有 0 件行） | 长尾被拟合为零表现为整行消失，不是留 0 行；一个错价直接按件数放大成错额 |
| 币种：cn 人民币、US 美元、DE 欧元、JP 日元、BR 雷亚尔、MX 比索 | 金额只在站点内比较，跨站点不相加 |
| SPU = 站点 + 平台 + product_id。Amazon 的 product_id 是父 ASIN、sku_id 是子 ASIN；淘宝是链接级（sku_id = product_id）；天猫是选项级，约七成行的 sku_id 是占位“0” | 占位 SKU 永远不能当跨父体的共同身份；同一个 product_id 在淘宝和天猫不是同一身份 |
| 同一父体的子体可以分属不同叶子（服务商按子体分配销量） | 类目内只汇总对应子体；上级 SPU 数重新去重，不把子类目的数相加 |
| 标题：Amazon 无 product_title，原文在 sku_title、服务商中文翻译在 product_title_cn；淘系只有 product_title | 判打标看中文标题，有疑义回原文 |
| product_listing_time 有 1970-01-01、1900-01-01 等占位值，且曾整批写成数据月份 | 不能直接当上市日期；首次有记录也不等于上市 |
| std_brand_name 中 “OTHERS/其他” 是未归入具名品牌的桶 | 不是品牌；它的占比是品牌归一化质量指标 |
| 治理层：现役发布 = gov_release 里 status='published' 且 built_at 最新；dws 聚合不含“其他”；scope 3.0.0 起含 BR/MX；gov_coverage_month 每月给 13 项覆盖率指标 | 对外出数走治理层；验收要核对发布与源表逐格一致 |
| 历史来源（服务商声明，2026-09-03）：2025-09 及之前由卖家精灵标化产品补充，只覆盖 TOP1000+ 级头部；2025-10 起为定制采集 | 2025-09/10 前后总量与 SPU 数不可直接比较，头部口径可比；2025 年及更早的“规模”系统性偏低是覆盖浅，不是市场小 |

**工具事实。** 源表按月分区：单月查询不到一秒，全历史查询要扫满全部月份（1–4 分钟），按站点过滤省不了扫描，所以视图都是一次算全部站点。大量分组上的 `COUNT(DISTINCT)` 很慢，先按 SPU 预聚合再计数。集群与线上 flywheel MCP 共用，查询工作组内存上限约 17 GB，重查询并行会被库杀掉（报 MinorGC kill overcommit），所以视图默认串行、失败自动重试一次；自己写的下钻尽量限定月份。doris MCP 对 `WITH` 开头的查询返回空数据而行数照报，且有行数上限——正式取证一律走 `scripts/q.py`。

## 2. 看的顺序与口径主次

1. **自顶向下**：国家×平台总量 → 标准一级 → 二级 → 三级 → SPU → SKU / 平台路径。先用国家总量序列定基调：每条路径都温和同涨的“普遍性偏高”在路径级排序里必然被淹没。
2. **分站点看**：排序、配额都在站点内做，不跨站点混排；一个站点的天文数字事故会把别的站点挤出视野。cn 展示可合并，质量问题按淘宝、天猫分别看。
3. **标准口径先行**：主战场是关注口径；平台类目与“其他”只用于定根因和写给服务商。每个问题都说明暴露度：完整传导（关注口径同样受影响）/ 部分渗入（给比例）/ 零暴露（只在“其他”或未打标里）/ 无观察（根本没有数据）。零暴露的问题仍写给服务商，但优先级降。
4. **全量历史**：每期重看全部月份，最大的问题可能在历史月。历史数值与上次推送不同是常态，不当信号。

## 3. 四项结果与变化贡献

主观测单位是国家、标准类目、SPU。四项结果：SPU 数、价格带、销量、销售额。

| 结果 | 观察什么 | 解释时区分 |
|---|---|---|
| SPU 数 | 有效商品数、出现 / 消失 | 新品、采集变化、打标变化；缺记录不代表退市 |
| 价格带 | 同一固定边界下各带 SPU 数与金额份额 | 同款变价与结构变化；均价不能替代分布 |
| 销量 | 件数、同比环比、子类与 SPU 的增减贡献 | 同款起量回落、估算变化；金额平稳也可能量价抵消 |
| 销售额 | 金额、同比环比、变化贡献 | 需求、促销、结构与数据缺陷 |

同一父类两期 C₀→C₁，互斥子集 A₀→A₁：
- 子集对父类净变化的贡献 = ΔA / ΔC，有正负、可超过 100%；ΔC 接近零时不按比值排名，先看正负抵消与绝对量。
- 拉动父类增长 = ΔA / C₀；C₀ 为零时不定义。
- 销量、金额两条线分别算，异常排序不能只看金额：量增价跌、量跌价涨会让金额平稳。
- 少数商品决定类目结果时优先级前移（例：类目 1,000 万→1,500 万，其中一个待核商品 200 万→650 万，贡献 90%、拉动 45 个百分点）。这只是定位了变化，还没证明它是错误。
- 已取得可信纠错值时，修正增长 = (C₁−E₁)/(C₀−E₀)−1；只把一组商品两期都剔除属于敏感性分析，改变了观察集合，不能冒称修正后的真实规模。

## 4. 病种指纹

| 病 | 指纹 | 与真实市场波动的区别 |
|---|---|---|
| 整体水位跳变（覆盖扩大或估算口径变更） | 站点总量台阶式跳变；行数、SPU 倍增；大量类目温和同涨；违反季节形态（淡季反涨最典型）；此后停在新台阶 | 真实市场不会让商品覆盖一夜倍增。新增商品贡献大 = 覆盖变化；头部 / 留存商品也同步涨 = 估算变更（更严重，历史不可比） |
| 观测覆盖不全 | 商品数与销量同向大跌，跨多个同级类目同月出现，消失远多于新增，头尾等比缩 | 真实需求下滑很少让商品数同步塌，更少跨类目同月共振 |
| 长尾截断 / 拟合为零 | 总量降而头部稳；≤5 件档商品占比骤变；中位数塌陷；整行消失 | 真实波动头尾同动；只有尾巴消失是拟合或采集行为 |
| 估算摆动 | 覆盖不变（SPU、行数稳）而同一批商品销量剧烈摆动 | 固定集合法加上年同期季节基线可把它与市场波动、覆盖变化分开 |
| 价格抓取异常 | 同款相邻月跳价（恰好约 10 倍 = 位数错误；≥50 倍多为占位价）；均价环比大而同款变价小 = 结构混入，同款也大 = 抓价 / 币种 / 单位错 | 金额由价 × 量推出，一个高销商品的错价能扭曲整条路径的金额 |
| 身份错联 | 不同商品共享占位 SKU 被并成一个；父子体换挂导致同一商品被算两次；跨平台同编号被当同实物；标题、品牌、平台路径说的不是同一件商品，一条商品撑起或扭转整个一级类目的金额 | 先按完整身份键核对，再谈量额；价格不跳时跳价检查拦不下，看单品集中度 |
| 类目错分（打标） | 叶子的大部分增长来自少数与定义不符的商品；“-其他”残差叶吸走具名兄弟叶的商品；本该关注的商品落进“其他”；同一 SKU 跨月换叶 | 用类目定义与机判规则逐条判标题；看错分商品对四项结果的贡献决定是否单列 |
| 采集范围漂移 | 采购范围内的平台路径断档或消失；范围外路径出现大量关注商品；根节点改名 | 先核对范围文件写法与生效期，再判漏采 |
| 品牌层病征 | 采集样本换血（增量来自新商品同时大量老商品消失）；留存商品估算抬升；OTHERS 占比上升；品牌数单月暴增后回落；增量集中在一两个商品；同一品牌多种写法 | 品牌增速与所在类目增速背离才是信号；同月同站点的类目事件多半同源，别当两个问题 |

## 5. 判别工具

**头部链接法。** 头部商品在任何采集深度下都会被覆盖，长尾随采集深度剧烈变化，所以头部的跨期对比能把“覆盖变了”和“估算变了”分开。
- TOP1000 占比台阶式下降且不回升 → 新增的量落在头部之外，是覆盖扩大的形状；占比不动而总量涨 → 头部同步涨，估算虚增嫌疑。
- 固定集合：基期 TOP1000 同一批商品到下一月的件数。要扣除排名回落（当月冲高进榜的商品次月自然回落，同源相邻月实测约 -5%~-9%：2025-08→09 德 -8.8%、日 -5.6%），并与上年同期同一对月份比较。显著偏离两者才是估算口径变化信号；集合消失数偏大也要警惕。
- 局限：只证明头部估算是否连续，不证明长尾正确；头部同口径上涨仍分不清“估算调整”和“真实热卖”，要叠加季节基线，Amazon 可再用 Sorftime。
- 跨来源（卖家精灵期 vs 自采期）只能用头部口径比较。

**新增 / 留存 / 消失拆解。** 涨幅来自新增商品 = 覆盖变化；两月都在的同一批商品大涨大跌 = 真实变化或估算调整，最需警惕。净值不变但大进大出比净值下降更可疑（采集样本换血）。

**最强判定链：固定集合 + 季节基线。** 覆盖不变而总量剧烈摆动时直接用：固定集合变化、上年同期基线、全量留存商品变化三条证据就能把估算摆动与市场波动 / 覆盖变化分开。

**同款跳价。** 先取前一个月价格再过滤，不能先按金额筛掉再取前值。带外高价先看标题与品牌排除“真贵货”（杂物型类目的高分位被海量低价配件压低，高端录音设备天然超带），再判错价、错币种、错单位。

**下钻到对象。** 一个类目的变化找到具体 SPU / ASIN 才算有结论：sql/drill/spu_changes.sql 给驱动商品，spu_trace.sql 给轨迹，platform_path_detail.sql 给平台路径明细。

**单品集中度。** 一个 SPU 占一级类目件额的比例、它对类目环比的贡献、两期都剔除它后的类目环比（04 摘要）。专抓跳价检查漏掉的失真：价格变化不到 3 倍，却靠错联的身份或失真的估算撑起整个类目。剔除后的环比是敏感性分析，不是修正值。

**叶子的平台类目构成。** 一个标准叶子的件额按平台类目节点拆开（09 摘要第六节）。抽样只看到每叶前几名，构成给出整叶：明文排除的商品挂在哪些节点、残差叶吸进了什么，按节点件额直接估整叶错分占比。平台类目是服务商的口径，专业商品也可能挂在大众节点下，结论写“按平台类目估”。

## 6. 判定语境

- **大促按当年实际日期核对**，不用固定日历（2026 年美、德 Prime Day 在 6 月）。常见窗口：cn 年货节（1 月）、38 节、618（5 月末–6 月）、99、双 11（10 月末–11 月）、双 12；US/DE Prime Day、秋季会员日（10 月）、黑五网一（11 月末）、圣诞季；JP 新生活季（3–4 月）、Prime Day、年末商战。大促月高涨、次月回落是预期形态；销量可提前或滞后，只有节日名称解释不了变化。
- 2 月天数少，环比自然下沉。
- BR/MX 自 2025-10 才有数据，2026-10 之前没有同比，环比噪声大。天猫体量最大，同幅度波动绝对影响最大。淘系没有外部交叉验证来源。
- 结构性正常：Amazon 的 category_3 为空表示路径只有两级；自写 SQL 的类目 join 一律 null-safe（`<=>`）；“其他”占采集量的大头是设计如此。
- 背景信息按来源分三栏：服务商声明（附日期，原话逐字）/ 库内实测（只描述现象）/ 我方推断（报告里标“推断，待确认”）。推断不得写成服务商行为或背景事实。

## 7. 方法级教训（提炼自案例库与审计，开工必读）

1. 先看站点总量序列再进类目；全站温和同涨在路径排序里看不出来（漏报德日 2026-01 跳变，用户一眼看出）。
2. 分站点看榜，不做全局排序。
3. 异常不等于错误：覆盖能力变化也表现为总量跳变；定性前先用头部两把尺子和新增 / 留存拆解区分覆盖与估算。
4. 推断不能写成服务商事实；服务商原话逐字记、附日期，不做时间线的二次加工。
5. 换口径要重扫，不能沿用旧结论；局部现象不外推全局，先全站复核；本品也按站点分别判断。
6. 品牌份额必须件数、金额双口径并分站点；跨站点汇总件数会掩盖站点间的反向运动；品牌均价大变说明采集到的商品结构变了。
7. 品牌层独立于类目层：类目全绿时品牌层仍可能坏；背离后必做新增 / 留存 / 消失拆解，留存商品大涨最可疑。
8. 价格与长尾每期必跑，不因主线忙跳过。
9. 全量重推下历史数值变动是常态，不做“重述检测”；只盯新月到货量级与历史月推丢 / 推薄。
10. 网格永远跑全时间线，最大的鱼可能在历史月。
11. 量级相近的成对出现 / 消失先怀疑 join 键（类目为空）再怀疑数据。
12. 外部评审或子 agent 的技术断言要逐条复算，修完必须实跑；空结果先查结构再下结论。
13. 报告给人读：通俗、指代清楚、按排查逻辑逐层下钻写到 ASIN；按模块逐一汇报状态，正面确认与问题同等重要；报告不写处置。
14. 身份必须带平台；占位 SKU 不能当身份。
15. 配置自身也会错：采购范围的写法要对源表核实（曾把日本全角＆写成半角 &、给中国 8 条范围多写一层中间类目，导致整年“缺失”误报）。
16. 无观测、零暴露、未发现异常是三种状态；没跑的检查写 ⏸️，不写正常。
17. 打标判定先定计法再分发：2026-09 七个子 agent 用了三种准则边界计法，各国不符率不可比，事后才统一。计法和交回格式写在 tagging.md，汇总用 tagging.py。
18. 估整叶错分先看叶子的平台类目构成，再决定要不要扩抽：2026-09 Amazon“耳机”叶 94%–99.6% 的件数在平台大众耳机节点下，一条单月查询就量化了，抽样只看到了前三名。
19. 跳价检查拦不住价格不跳的单品失真：2026-09 日本一条标题、品牌、平台路径互相矛盾的舞台灯，价格只变 1.3 倍，却占日本灯光类 9 月金额 38%，并把 8 月环比从 -6.7% 抬成 +23.5%。单品集中度每期必看。

## 8. 证据链与置信

每个问题：现象 → 已做检查 → 排除了什么 →（必要时外证）→ 定性 → 置信（高 / 中 / 低）→ 影响（四项结果、暴露度）→ 证据位置（运行目录里的 SQL 与结果文件）。拿不准就标低置信并写下一步要什么证据，不含糊定性。贡献是分解不是因果；统计相关、标题相近、编号相同都不能单独证明因果或同一实物。
